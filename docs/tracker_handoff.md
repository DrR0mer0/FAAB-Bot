# Baseline tracker — handoff note

Written at the end of the session that built phase 1 (commit `03c5fce`, 2026-10-03), and updated later the same day for three changes made before the first cycle: the Sunday slot rule (decision 2), raw ownership responses moved out of the DB (decision 5), and the scheduled tasks (see "Scheduled tasks"). Read this before touching `tracker/`. This note adds the *why* and the traps beyond `CLAUDE.md`/`README.md`.

## Purpose
Answer one question honestly: **is O.D.D.S. better than chance?** Every run is logged to an append-only ledger beside three dumb baselines drawn from the same pool, then scored against actual results.

## Design decisions (from the user's answers) and why
1. **Headline K=10, also K=25, each with its own matched position mix.** Top-10 matches the P@10 history; baselines copy O.D.D.S. production's mix per pick set so a position-mix edge can't pass as skill (Group 2's artifact). The shadow model is logged but is its own model, not a matched baseline.
2. **Per-slot refusal, and a per-slot pool.** The Sunday *main slate* starts at the first Sunday kickoff at or after 1:00 PM ET (`tracker.main_slate_start`). `sun` must be logged before that; `thu` before the first game that precedes it. **International/early-Sunday games are treated exactly like Thursday games** (user decision, 2026-10-03; rule recorded per run as `slot_rule: main-slate-v2` in `tr_runs.run_config_json`): a 9:30am ET London kickoff does *not* close the `sun` slot, and its players are not in the `sun` pool. A week with no game before the main slate has no `thu` slot; a week with only an international game before it *does* (closing at that kickoff). A whole-week refusal would block every Sunday run (Thursday's game has started), so instead **a slot's pool only holds players whose game kicks off at or after the slot's cutoff** (`tracker.split_pool_at_cutoff`, applied to `score_week.py`'s scored pool; excluded ids are stored in `run_config_json`). That is deliberately independent of *when* the run happens: `score_week.py`'s own kickoff guard only drops games that have already started, so a `sun` run made on Saturday would otherwise still contain the London players.
3. **League scoring for the tracker; flag the label mismatch only.** The model's labels were built with a 4-pt passing TD; fixing that changes the model, so it waits for the separate retrain.
4. **Report two hit types, both under league scoring.** *Top-24 at position* = "does it help me win"; *spike week* (≥1.5× trailing-3 avg and ≥10) = "does O.D.D.S. beat chance at its own job." Spike is recomputed in the tracker from league-scored points — **never read from `labels_player_week.spike_flag`** (4-pt labels).
5. **Roster-%: ESPN `percentOwned` daily (primary), Sleeper trending adds (secondary), raw responses kept, failures loud but never fatal.** Yahoo is blocked; Sleeper has no ownership field. ESPN's endpoint is unofficial, so every fetch is shape-validated. **Storage (user decision, 2026-10-03):** the DB keeps the parsed rows (`tr_ownership`: player_id, percent_owned, percent_change, ..., joined to the snapshot's `taken_at`) and, per snapshot, the SHA-256 of the raw response plus the name of its file. The raw response itself is a gzip file under `raw/ownership/` (gitignored; `<UTC timestamp>_<source>_<sha256[:12]>.json.gz`), so old ones can be moved to an archive later — the hash still identifies them. `--ownership-raw-dir` overrides the folder.
6. **Ownership is snapshotted into the pool at `log` time, and the under-50% subset is its own full scoreboard** (every model re-picks from that smaller pool) — the actual sleeper test, not a footnote. It can't be backfilled, so backtests can't have it.
7. **Snap counts from nflverse `snap_counts`** (new `tr_snap_counts`, PFR→gsis via `players.csv`). Heuristic = mean offense snap % of last 2 games minus the 2 before; ties → target share, then player_id; no 4 prior games → ranks last. Each run records the newest snap week it had (`tr_runs.snap_week_used`); the release lags ~a day.
8. **All five models logged:** `odds_prod`, `odds_shadow`, `dart`, `heuristic`, `last_week`.
9. **Backtest (phase 2): train as production does, score with as-of features, flag the leak, no model-logic changes.** Separately a TODO to retrain with `starter_absent_proxy` as-of (or removed), logged as a new model_version so old vs fixed compare.
10. **Pool rule: nobody designated Out or Doubtful at log time** (user decision, 2026-10-04; `pool_rule: exclude-out-doubtful-v1` in `tr_runs.run_config_json`; **starts with week 5**). Found after the first real run: its pool held six players already ruled Out (DeVonta Smith, Justin Jefferson, Breece Hall, Caleb Williams, Baker Mayfield, Ko Kieft) -- `score_week.py`'s availability gate only sees roster statuses (IR etc.), not weekly game designations. Such a pick can't score for *any* model or dart draw, so it is a pool rule applied to all of them alike, in the tracker (`tracker/injuries.py`), not a model change. Why these two statuses: of 2,363 skill-position player-weeks designated Out in 2016-2024 none recorded a stat, and 3 of 442 Doubtful did; Questionable players play 60% of the time and stay in. **Source of record: nflverse's `injuries` release** (the official report, gsis ids on every row, history back to 2009 -- the same source the retrain will train on). It is refreshed nightly at 06:00 UTC (11 PM Pacific, on time every day checked) and again a few hours later at an unreliable time, so the nightly file is what both 07:00 runs see; `log` treats a file older than `injury_report_max_age_hours` (20) as missing. **ESPN's `injuryStatus`** (parsed from the roster-% snapshot the run already pins, stored in `tr_ownership.injury_status`) is the cross-check -- disagreements are printed and stored with the run -- and decides the pool only when the nflverse file is missing; ESPN is editorial, not the official report. If neither is available the run is still logged, loudly, with the rule not applied and that recorded. Each run stores the excluded ids and statuses, the source, the report's SHA-256, and a gzip copy of the report in `raw/injuries/`. Inherent limits: a `thu` run only knows Thursday-game designations (Sunday teams aren't designated until Friday), and nothing knows game-day inactives at 07:00.
- **Display flag, not a score change:** `log` re-renders the prediction markdown with **(OUT)** / **(DOUBTFUL)** next to those players' names plus a one-line note (`score_week.render_markdown_report(output, status_flags, flag_note)`). Scores, ranks, row order, the JSON and `verify_week.py` are untouched, and without the two arguments the renderer's output is byte-identical to before. A hand-run `score_week.py` or `render_prediction_report.py` produces an unflagged file. Taking Out/Doubtful players out of `score_week.py`'s own pool waits for the retrain.
- Also: committed JSONL export of every run's rows (`tracker/ledger_export/`), because the DB is gitignored and triggers aren't tamper-proof.

## Confirmed league scoring
0.5 PPR · 6-pt rushing/receiving TD · **5-pt passing TD** · −2 INT · 0.04/passing yd · 0.1/rush & rec yd · −2 fumble lost · +2 per 2-pt conversion. Lives in `tracker/hit_config.json`; `scoring`, `hit` and `crowd_hit` sections are hashed and the hash is stored with every scored week.

## Known issues / open TODOs
- **`starter_absent_proxy` leaks — and makes live scores depend on DB load timing (retrain is now the top backlog item).** In the training table it uses whether the presumed starter played in the week being predicted (~94% populated); at live scoring it is `None` *only while the DB holds no rows for that week* — load the week's Thursday game and it flips to 1 for most of the pool (see the `log` guard below). It's a production feature. The planned label-shuffle check **cannot** catch this (shuffled labels stop matching a leaking feature too); use an as-of recomputation diff (week W's features with week W-onward data removed). Flagged in every report.
- **4-vs-5 label mismatch:** `half12` profile has a 4-pt passing TD. Fix in the same retrain.
- **Sleeper/ESPN name-match fallback:** when the `espn_id` crosswalk misses, ids are matched by *unique* normalized name+position against `ref_players` (never guesses on ambiguity). It lifted Sleeper trending from 27→87 of 100 mapped, ESPN to 957/960. Unaudited for wrong matches, and ids are frozen at snapshot time (append-only), so the earliest snapshots have lower coverage (snapshots 3-4 ran with a broken name-suffix regex that matched nothing, fixed afterward — they simply under-match, they don't mis-match). The Sleeper feed isn't used in any metric yet.
- ESPN raw responses are ~3.6 MB compressed each (~400 MB/season with Sleeper's). They no longer bloat the DB — they're files in `raw/ownership/` — but nothing archives or prunes that folder yet. If a file is moved away, `tr_ownership_snapshots.raw_file` still names it and `raw_sha256` still verifies it.
- **`log` refuses unless the DB holds every already-played game of the weeks before the one being logged** (`tracker.played_games_not_loaded`, part of `check_data_fresh`): `player_week_stats` rows for both teams of each such game, and a `labels_player_week` row for every one of those stat rows (`opponent_position_matchup` reads fantasy points from the labels, so stats loaded without `generate_labels_and_breakouts.py` would silently score that week as 0 allowed). The older guards only looked at `nfl_games` scores and the stats *CSV*, so a game whose players never reached the DB (typically Monday night, published late) passed unnoticed.
- **`log` refuses if the DB already holds rows for the week being logged** (`tracker.target_week_rows_in_db`). Why it matters: `load_nflverse_into_history_SAFE_v3.py` without `--through-week` loads every week in the stats CSV, including the already-played games of the week being predicted, and any week-W `player_week_stats` row makes `score_week.py` compute `starter_absent_proxy` from a partial week — 1 for every non-starter whose team simply hasn't played yet. So until the retrain fixes that feature, **live scores depend on when the DB was last loaded**; the guard plus `--through-week` (see "Weekly cycle") keep the DB in the one state where the feature is `None` for everyone, which is how every logged run must be scored to stay comparable. The guard does not need to cover `nfl_games` or `team_week_stats`: no feature reads game results from them (see `CLAUDE.md`, Known model limitations, for the check).
- **Week 4's `sun` run (the first in the ledger) predates the Out/Doubtful pool rule** and is left as logged; reports footnote any run without a `pool_rule`. One heuristic top-10 pick (DeVonta Smith) and four top-25 picks across models were Out; no O.D.D.S. top-10 pick was.
- **`tr_ownership.injury_status` is NULL for the snapshots taken before 2026-10-04's change** (ids 1-7); the statuses are still in those raw files.
- **ESPN lists a newly added player before giving him an `ownership` block.** On 2026-10-05 one such record (of 961) failed both snapshots of the day (ids 9 and 11, `ok=0`; a third, id 13, was taken after the fix). The parser now skips records with no ownership data, stores the count (`tr_ownership_snapshots.n_skipped`), prints the names, and fails only if under 98% of the records are valid (`MIN_ESPN_VALID_SHARE`) — a real shape change takes that share to about zero.
- **Week 12 (Thanksgiving) has a Wednesday-night game (Nov 25, 8:00 PM ET).** The `thu` task runs Thursday morning, after that slot has closed, and will refuse loudly. Log week 12's `thu` slot by hand before Wednesday evening.
- The scheduled `log` jobs refresh the nflverse *files* but do not run the DB loader. If a kickoff time moves (flex scheduling, week 18) and the weekly loader hasn't been re-run, `nfl_games` — and so the slot cutoff — is stale.

## Weekly cycle (in season)
W = the week about to be played; W-1 = the week that just finished.

**Tuesday, after Monday night's stats are published** — the only time the DB is loaded:
```
python data/fetch_weekly_update.py --season 2026
python data/load_nflverse_into_history_SAFE_v3.py --seasons 2026 --through-week <W-1>
python model/generate_labels_and_breakouts.py --seasons <all loaded seasons incl. 2026> --through-week <W-1>
python tracker/tracker.py fetch-snaps
python tracker/tracker.py score --season 2026 --week <W-1>
python tracker/tracker.py report --season 2026 --week <W-1>
```
(`evaluation/verify_week.py` for W-1 belongs here too, as before.) Always pass `--through-week <W-1>`, even on a Tuesday when the CSV can't contain week W yet: it's what makes a late or repeated load (Friday, Saturday) safe.

**Thursday and Sunday mornings** — the `log` tasks run on schedule; nothing to do by hand unless one fails. They refresh the nflverse *files* only and never load the DB.

Two refusals in `log` enforce this (both in `check_data_fresh`, both before O.D.D.S. runs, both a FAILED line + message box from a scheduled run):
- **Too little:** an already-played game from a week before W is missing from `player_week_stats`, or its stat rows have no `labels_player_week` row (`played_games_not_loaded`). Fix: run the Tuesday load.
- **Too much:** the DB holds *any* `player_week_stats` or `labels_player_week` row for week W itself (`target_week_rows_in_db`; the message names the games). That is what an uncapped load after Thursday's game produces. Fix: delete the week-W rows from both tables, then log.

## Scheduled tasks (Windows Task Scheduler, folder `\FAAB\`)
Registered 2026-10-03 for the logged-on user by `python tracker/scheduled_run.py install` (re-run to replace them; `uninstall` removes them; `status` shows them and the last runs). Times are the PC's local time:

| Task | When | Runs |
|---|---|---|
| `tracker-snapshot-ownership` | daily 06:30 | `tracker.py snapshot-ownership` |
| `tracker-log-thu` | Thursdays 07:00 | `data/fetch_weekly_update.py`, then `tracker.py log --auto --slot thu` |
| `tracker-log-sun` | Sundays 07:00 | `data/fetch_weekly_update.py`, then `tracker.py log --auto --slot sun` |

- Each run writes `tracker/logs/<timestamp>_<job>.log` and one line in `tracker/logs/scheduled_runs.log` (gitignored).
- `log --auto` resolves the current week from `nfl_games` and **skips quietly (exit 0)** when the week has no such slot or the slot is already in the ledger — so logging a slot by hand first is fine. Anything else is a **failure: non-zero exit, a FAILED line, and a message box that stays up until dismissed**; none of the failure paths writes to the ledger.
- Tasks use "run as soon as possible after a missed start" and never wake the PC. Woken late the same day, `log` decides from the real kickoff instants (logs if the window is still open, refuses if not). Woken on a *different* day, a log job refuses to run at all (`MISSED`): by then `--auto` would resolve to the next week and log it days early.
- The refresh step exists because `log` refuses on a weekly-roster file older than 3 days — without it a Sunday run could never pass. It only rewrites files in `nflverse_raw/`; the loader, `fetch-snaps`, `score` and `report` remain the manual weekly cycle, and `log` refuses if the DB is behind.
- **A scheduled `log` is a real, permanent ledger entry.** `tr_runs.repo_git_commit` records `HEAD` at run time, so commit tracker changes before a slot is logged.

## What a fresh session would get wrong
- **`log` runs `score_week.py` itself and writes the committed prediction files.** Don't hand-run it for the same snapshot. First run of a week keeps the bare name (`2026_week05.json`, what `verify_week.py` reads); a later one becomes `_sunday`. It never overwrites.
- **The ledger is append-only and `log` refuses re-logging a (season, week, slot).** Never test against the real DB — use `--db <copy> --predictions-dir <scratch> --export-dir <scratch>` (and `--as-of` only for testing). A bad real run is permanent.
- **`nfl_games.kickoff_utc` is US/Eastern, not UTC.** Reuse `score_week.parse_kickoff_utc`; don't re-derive it.
- **Scoring reads the raw `stats_player_week_<season>.csv`, not the DB** — the DB loader never carried the 2-pt columns. Spike baselines walk back through consecutive on-disk seasons and stop at the 2019 gap.
- **The tracker doesn't replace `verify_week.py` / `verification_log.json`** — both still run and still use the 4-pt `spike_flag`; numbers can differ slightly.
- **`u50` is strictly `<50` for players whose ownership is known, and a pool player with NO row in the snapshot used stays IN it, flagged as "ownership unknown"** (user decision, 2026-10-05; `sleeper_pool_rule: under-threshold-or-unknown-v2` plus the ids in `run_config_json`). The flag is `tr_pool.percent_owned IS NULL` with `in_u50 = 1` — unknown is not treated as 0% or as under 50%, the player just isn't silently lost, and reports show the count per run. Week 4's run (no `sleeper_pool_rule` key) dropped such players — one, Mike Washington Jr. — and reports say so. Two things to keep in mind: with **no snapshot at all** there is still no sleeper pool (everyone would be "unknown"); and a widely owned player whose ESPN id fails to map to a gsis id would enter the sleeper pool as unknown — `log` prints the names every run and raises a banner when fewer than 80% of the pool matched.
- **Which roster-% snapshot a run uses:** the newest successful ESPN snapshot no older than 36h at log time (`ownership_max_age_hours`); failing that, one live attempt; failing that, the run is logged without ownership and has no sleeper pool. It never falls back to an older snapshot. A snapshot older than 12h at log time (`ownership_stale_note_hours`, i.e. not that morning's) is used but footnoted in reports. Measured so far, 1-2 of ~320 pool players cross 50% per day outside a waiver run; nothing measured across one yet.
- **A 1-week report is not a result.** Don't cite tracker numbers until the small-sample note goes away.
- Windows: native Python won't resolve Git-Bash `/c/...` paths inside Python code; use `C:\...` or relative paths. Tests: `python -m unittest discover -s tracker -v` from the repo root.
- **A live `log` fetches the injury report; an `--as-of` run does not** (today's report would be from that run's future) and records `injury.source: skipped`. Tests that exercise the rule patch `tracker.utcnow` and `tracker.injuries.fetch_nflverse` instead of passing `--as-of`.
- **`take_snapshot` needs an explicit raw dir** (no default, on purpose) — a test that forgets it fails instead of writing into the real `raw/ownership/`.
- First loggable slot at handoff: week 4 `sun`, any time before 1:00 PM ET Sunday 2026-10-04 (the pool excludes PIT/CLE, already played, and IND/WAS, the 9:30am London game); the `tracker-log-sun` task will log it at 07:00 local that morning if it hasn't been logged by hand. Otherwise week 5 `thu`.
