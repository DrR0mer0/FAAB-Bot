## Purpose
Answer one question honestly: **is O.D.D.S. better than chance?** Every run is logged to an append-only ledger beside three dumb baselines drawn from the same pool, then scored against actual results.

## Design decisions (from the user's answers) and why
1. **Headline K=10, also K=25, each with its own matched position mix.** Top-10 matches the P@10 history; baselines copy O.D.D.S. production's mix per pick set so a position-mix edge can't pass as skill (Group 2's artifact). The shadow model is logged but is its own model, not a matched baseline.
2. **Per-slot refusal, and a per-slot pool.** The Sunday *main slate* starts at the first Sunday kickoff at or after 1:00 PM ET (`tracker.main_slate_start`). `sun` must be logged before that; `thu` before the first game that precedes it. **International/early-Sunday games are treated exactly like Thursday games** (user decision, 2026-10-03; rule recorded per run as `slot_rule: main-slate-v2` in `tr_runs.run_config_json`): a 9:30am ET London kickoff does *not* close the `sun` slot, and its players are not in the `sun` pool. A week with no game before the main slate has no `thu` slot; a week with only an international game before it *does* (closing at that kickoff). A whole-week refusal would block every Sunday run (Thursday's game has started), so instead **a slot's pool only holds players whose game kicks off at or after the slot's cutoff** (`tracker.split_pool_at_cutoff`, applied to `score_week.py`'s scored pool; excluded ids are stored in `run_config_json`). That is deliberately independent of *when* the run happens: `score_week.py`'s own kickoff guard only drops games that have already started, so a `sun` run made on Saturday would otherwise still contain the London players.
3. **League scoring for the tracker; flag the label mismatch only.** The model's labels were built with a 4-pt passing TD; fixing that changes the model, so it waits for the separate retrain.
4. **Report two hit types, both under league scoring.** *Top-24 at position* = "does it help me win"; *spike week* (≥1.5× trailing-3 avg and ≥10) = "does O.D.D.S. beat chance at its own job." Spike is recomputed in the tracker from league-scored points — **never read from `labels_player_week.spike_flag`** (4-pt labels).
5. **Roster-%: ESPN `percentOwned` daily (primary), Sleeper trending adds (secondary), raw responses kept, failures loud but never fatal.** Yahoo is blocked; Sleeper has no ownership field. ESPN's endpoint is unofficial, so every fetch is shape-validated. **Storage (user decision, 2026-10-03):** the DB keeps the parsed rows (`tr_ownership`: player_id, percent_owned, percent_change, ..., joined to the snapshot's `taken_at`) and, per snapshot, the SHA-256 of the raw response plus the name of its file. The raw response itself is a gzip file under `raw/ownership/` (gitignored; `<UTC timestamp>_<source>_<sha256[:12]>.json.gz`), so old ones can be moved to an archive later — the hash still identifies them. `--ownership-raw-dir` overrides the folder.
6. **Ownership is snapshotted into the pool at `log` time, and the under-50% subset is its own full scoreboard** (every model re-picks from that smaller pool) — the actual sleeper test, not a footnote. It can't be backfilled, so backtests can't have it.
7. **Snap counts from nflverse `snap_counts`** (new `tr_snap_counts`, PFR→gsis via `players.csv`). Heuristic = mean offense snap % of last 2 games minus the 2 before; ties → target share, then player_id; no 4 prior games → ranks last. Each run records the newest snap week it had (`tr_runs.snap_week_used`); the release lags ~a day.
8. **All five models logged:** `odds_prod`, `odds_shadow`, `dart`, `heuristic`, `last_week`.
9. **Backtest (phase 2): train as production does, score with as-of features, flag the leak, no model-logic changes.** Separately a TODO to retrain with `starter_absent_proxy` as-of (or removed), logged as a new model_version so old vs fixed compare.
10. **Pool rule: nobody designated Out or Doubtful at log time** (user decision, 2026-10-04; `pool_rule: exclude-out-doubtful-v1` in `tr_runs.run_config_json`; **starts with week 5**). Found after the first real run: its pool held six players already ruled Out (DeVonta Smith, Justin Jefferson, Breece Hall, Caleb Williams, Baker Mayfield, Ko Kieft) -- `score_week.py`'s availability gate only sees roster statuses (IR etc.), not weekly game designations. Such a pick can't score for *any* model or dart draw, so it is a pool rule applied to all of them alike, in the tracker (`tracker/injuries.py`), not a model change. Why these two statuses: of 2,363 skill-position player-weeks designated Out in 2016-2024 none recorded a stat, and 3 of 442 Doubtful did; Questionable players play 60% of the time and stay in. **Source of record: nflverse's `injuries` release** (the official report, gsis ids on every row, history back to 2009 -- the same source the retrain will train on). Inherent limits: a `thu` run only knows Thursday-game designations (Sunday teams aren't designated until Friday), and nothing knows game-day inactives at 07:00.

15. **Breakout-trend observations: PRE-REGISTRATION (fixed 2026-10-20, user decisions the same day; nothing computed yet).** Question: does O.D.D.S. find players on a breakout *trend*, not just single-week spikes? Measurement only -- no model change, and never part of the official spike/top-24 record. The definitions below were written down before any trend number was computed for 2026; they are not to be tuned after seeing results. A later change is a new, separately labelled version (new `trend` hash), and the earlier version's results stay on record. **Built 2026-10-22** -- see *As built* at the end of this decision.
- **Which runs.** One run per week, the official first snapshot (`thu` if the week has one, else `sun`), as in the season summary's record. Pick sets as logged: all/u50 x top 10/25, for odds_prod, odds_shadow, heuristic, last_week and dart. Dart is evaluated over the same 1000 draws the scoring uses (`rebuild_dart_sets`), each model reported as a percentile of the dart distribution; draw i of consecutive weeks is treated as one dart "season" for the de-duplication below.
- **Season limit.** Every window ends by week 17 (the league's last playoff week). Payoff is evaluated only for picks in weeks <= 14; role growth only for weeks <= 15; crowd/league-add windows are 14 days and need no cut.
- **(A) Multi-week payoff, per pick.** *Baseline* B = the spike baseline already used by the tracker: mean league-scoring points over his last 3 played games before week W (fewer than 3 prior games: not evaluated, as for spikes). *Payoff* P = mean league-scoring points over weeks W..W+3 in which his team played -- a bye is skipped, a team game he didn't play counts 0 (DNP with the team playing = 0; a lost role is the opposite of a trend). League scoring = the tracker's current scoring version, from the stats CSV, with the same stat-correction check as the spike scoring. **Primary:** *sustained breakout* = P >= 1.5 x B and P >= 10 points per game (the spike rule's multiplier and floor, over four weeks). **Secondary:** lift = P - B, points per game.
- **(B) Role growth, per pick.** *Snap share* (primary, every position): mean offense snap % (nflverse `snap_counts`) over weeks W..W+2 minus the mean over W-3..W-1, each window over the weeks his team played (byes skipped, a team game with no snap row = 0%); each window needs at least 2 such games, else not evaluated. *Target share* (secondary, RB/WR/TE): the same difference in nflverse's weekly `target_share`. A *role-growth hit* is a difference at or above the 90th percentile of that position's distribution over every player-week of 2022-2025 computed with exactly these rules -- the cut-offs are computed from history and written into `hit_config.json` BEFORE any 2026 role-growth number is computed, and are not recomputed afterwards. Known trap: the snap-share heuristic ranks on the four weeks before W, which overlap the "before" window, so its picks start that window high and regress -- read it against dart, not head-to-head.
- **(C) crowd_hit, fixed.** Definition unchanged (under 50% ESPN-owned at pick time; a hit if any ESPN snapshot in (log time, log time + 14 days] shows it over 50%; unknown ownership or >= 50% at pick time: not applicable). Changes: dart over the 1000 draws as a percentile instead of the one stored draw; one run per week (no double counting of thu and sun); reported in the observation block below.
- **(D) League add (new).** Eligible: a pick who was available in the user's own Yahoo league at log time (in that run's league-availability snapshot, `tr_league_availability`: free agent or waivers). Hit: any add of that player by ANY team in the league in (log time, log time + 14 days], from the newest `lg_transactions` snapshot (waiver claims and free-agent adds; trades don't count). Runs without a league-availability snapshot (week 4 `sun`, week 5 `thu`) can't say who was available and are not evaluated. **Shown in tracker reports only, never in the newsletter**, as aggregate counts and rates per model and pick set -- no team or manager names.
- **De-duplication.** In the season aggregate, a player picked by the same model in the same pick set in consecutive weeks counts once, at the first pick of the stretch (dart: per draw sequence). Per-week tables show every pick.
- **Intervals.** None until 8 weeks have resolved for that metric -- point estimates and dart percentiles only. From 8 weeks: a moving-block bootstrap over weeks with block length = the window (4 weeks for payoff, 3 for role growth, 2 for crowd and league add), because consecutive windows overlap and the same players recur; the ordinary week bootstrap of the official record would overstate the confidence.
- **When each resolves** (after the Tuesday load of the last week it needs): week 4 run -- role growth now (weeks 1-3 vs 4-6), payoff 10-27; week 5 -- role growth and crowd 10-27, payoff 11-03; week 6 -- role growth and crowd 11-03, payoff 11-10; week W -- role growth after W+2, payoff after W+3, crowd/league add about two weeks after the run.
- **Where it appears.** Season summary: a new section "Observation only: breakout trends", after the Sunday section and separate from the official record -- per model and pick set: picks evaluated, sustained breakouts, mean lift, mean snap / target-share change, role-growth hits, crowd hits, league adds, each with its dart percentile; the header lists the weeks resolved and pending. Weekly scoreboard: one line, "week W's trend windows resolve after week W+3". The existing "Crowd hits (secondary metric)" table moves into that section.
- **Storage.** An append-only `tr_trend_results` table (built as `tr_trend_outcomes`, one row per POOL player rather than per pick -- see *As built*) (like `tr_crowd_results`), filled once per run when each window closes, by `score`; definitions in a new `trend` section of `hit_config.json` with its own hash, kept OUT of the hash that defines the official record so weeks already scored don't look re-defined.
- **As built (2026-10-22).** `tracker/trends.py`, run by every `score` after the crowd step. It appends one `tr_trend_outcomes` row per POOL player per official run per metric (payoff, snap_growth, target_growth, crowd, league_add), once per `trend` hash, when that window has closed. Storing the whole pool lets any pick set be judged later, a model's picks or each of the 1000 dart draws, rebuilt with `baselines.rebuild_dart_sets` / `dart_draws`, and makes the de-duplication possible for dart too. The definitions are in `hit_config.json`'s `trend` section, hashed by `trends.trend_hash` and kept out of `scoring.config_hash`, so the official hash is unchanged (`476e6708f0`). The role-growth cut-offs come from `tracker.py trend-cutoffs --write` (refused once any role outcome is stored): snap share QB +31.0, RB +15.3, TE +17.3, WR +21.5 percentage points, and target share RB +4.3, TE +5.0, WR +6.8, the 90th percentile over 3,948-12,000 player-weeks of 2022-2025 per position. Snap and target counts are equal because eligibility depends only on team games. Implementation details the pre-registration left open: a player's team per week is the nflverse weekly roster's (2026), else his snap/stats rows' nearest earlier week; a payoff window needs at least one team game; league add counts waiver and free-agent adds (trades don't); a run without a league-availability snapshot is 'not evaluable' and stores nothing; payoff and role growth refuse picks before week 4 (`trends.FIRST_PICK_WEEK`, a code constant so the trend hash stays `eb9fc142cb`; added when no outcome was stored and no run predated week 4, so nothing changed). Report: the season summary's "Observation only: breakout trends" section (after the Sunday section) replaces the old crowd table, which `compute_crowd` still fills; the weekly scoreboard carries one line. **Not built:** a stat-correction re-check of stored payoff outcomes -- the spike scoring has one, the trend payoff does not yet; until it does, a correction to weeks W..W+3 after a payoff is stored is not flagged.
- Also: committed JSONL export of every run's rows (`tracker/ledger_export/`), because the DB is gitignored and triggers aren't tamper-proof.

## Weekly cycle (in season)
W = the week about to be played; W-1 = the week that just finished.

**Tuesday, after Monday night's stats are published** — the only time the DB is loaded:
```
python data/fetch_weekly_update.py --season 2026
python tracker/tracker.py check-stats --season 2026        # were earlier, already-scored weeks corrected? (exit 1 if so)
python data/load_nflverse_into_history_SAFE_v3.py --seasons 2026 --through-week <W-1>
python model/generate_labels_and_breakouts.py --seasons <all loaded seasons incl. 2026> --through-week <W-1>
python tracker/tracker.py fetch-snaps
python evaluation/verify_week.py --season 2026 --week <W-1>   # the frozen first snapshot against the DB labels
python tracker/tracker.py score --season 2026 --week <W-1>
python tracker/tracker.py report --season 2026 --week <W-1>
python tracker/tracker.py report --season 2026                # season summary
python league/league_data.py snapshot                         # only if the 06:35 task failed: it fetches W-1's final lineups
python league/newsletter.py build --week <W-1>                # the league recap, into gitignored league_data/newsletter/
```
Back up the DB before the load (`faab_history_core_v0_1.pre_week<N>_load.bak.db`). Then commit, as separate commits, the prediction files and ledger export of any run logged since the last commit, and the week's verification, scoring export and reports. Daily, with nothing to do by hand: 06:30 roster-% snapshot, 06:35 league snapshot and activity report. Always pass `--through-week <W-1>`, even on a Tuesday when the CSV can't contain week W yet: it's what makes a late or repeated load (Friday, Saturday) safe.

**Stat corrections.** nflverse revises stats after the fact. Every scoring stores the stats file's SHA-256 and a *fingerprint* of what it actually read (`scoring.stats_fingerprint`: week, player, position, team and league points for the regular-season rows through the scored week that scoring can see — rows at a hit position (QB/RB/WR/TE) plus any row of a pool player; the week itself for points and ranks, earlier weeks for the spike baselines). It carries a version prefix (`v2:`); a scoring with an older or missing fingerprint reads as "unknown", never "changed". v1 covered every row and its first alarm (2026-10-08) turned out to be nflverse re-labelling a guard as a center and a DE as an LB — nothing scoring reads — hence v2. The file hash alone is useless for this: the season file gains a week of rows every Tuesday. `check-stats` compares each scored week's latest scoring with the file as it is now; `score` runs the same check on every already-scored week each time it is used (including when it skips a week already scored), and `report` puts a warning at the top of any report whose week changed. A changed week says how many of its own player scores differ (0 = the correction is in an earlier week, i.e. only baselines moved). Nothing re-scores by itself: run `score --season Y --week N --force`, which **appends** a corrected scoring (results are never overwritten; reports always read a week's newest scoring) and clears the warning. Week 4 has three identical scorings for these reasons: scoring 1 predates fingerprints, scoring 2 was appended the same morning from the same file to set a baseline, and scoring 3 (2026-10-08) followed that first alarm and a reload of stats and labels through week 4 — no result changed, and it carries the v2 fingerprint. Limits: a baseline that reaches into the prior season (weeks 1-3) is outside the fingerprint, and `verify_week.py` has its own record (DB labels) that a re-score doesn't touch.

**Thursday and Sunday mornings** — the `log` tasks run on schedule; nothing to do by hand unless one fails. They refresh the nflverse *files* only and never load the DB.

Two refusals in `log` enforce this (both in `check_data_fresh`, both before O.D.D.S. runs, both a FAILED line + message box from a scheduled run):
- **Too little:** an already-played game from a week before W is missing from `player_week_stats`, or its stat rows have no `labels_player_week` row (`played_games_not_loaded`). Fix: run the Tuesday load.
- **Too much:** the DB holds *any* `player_week_stats` or `labels_player_week` row for week W itself (`target_week_rows_in_db`; the message names the games). That is what an uncapped load after Thursday's game produces. Fix: delete the week-W rows from both tables, then log.

## Scheduled tasks (Windows Task Scheduler, folder `\FAAB\`)
Registered 2026-10-03 for the logged-on user by `python tracker/scheduled_run.py install` (re-run to replace them; `uninstall` removes them; `status` shows them and the last runs). Times are the PC's local time:

| Task | When | Runs |
|---|---|---|
| `tracker-snapshot-ownership` | daily 06:30 | `tracker.py snapshot-ownership` |
| `tracker-log-thu` | Thursdays 07:00 | `data/fetch_weekly_update.py`, then `tracker.py log --auto --slot thu`, then `tracker.py check-stats` (advisory) |
| `tracker-log-sun` | Sundays 07:00 | `data/fetch_weekly_update.py`, then `tracker.py log --auto --slot sun` |
| `league-snapshot` | daily 06:35 | `league/league_data.py snapshot`, then `league_data.py report` (added 2026-10-10 with `install --job league`) |

- **`league-snapshot` is not a tracker job** — it only shares the runner. It snapshots the user's Yahoo league into the `lg_*` tables (see `CLAUDE.md`, League data layer); no prediction run reads them, its failure box says so, and a report that can't be written is only a note on its summary line. `install --job <name>` registers one task and leaves the others alone.
- **The Thursday job's `check-stats` step is advisory.** If nflverse has corrected a week that is already scored, a separate message box names the week and gives the `score --force` command, and the run's summary line gets a note. It never changes the job's exit status or OK/FAILED line, runs whether the log step logged, skipped or refused, and a check that can't run is only noted. Re-scoring stays a manual decision.
- Each run writes `tracker/logs/<timestamp>_<job>.log` and one line in `tracker/logs/scheduled_runs.log` (gitignored).
- `log --auto` resolves the current week from `nfl_games` and **skips quietly (exit 0)** when the week has no such slot or the slot is already in the ledger — so logging a slot by hand first is fine. Anything else is a **failure: non-zero exit, a FAILED line, and a message box that stays up until dismissed**; none of the failure paths writes to the ledger.
- **Triggers and settings (changed 2026-10-14).** Each task fires at its time AND 2 minutes after the user signs in; it wakes the PC from hibernate (`WakeToRun`; wake timers are enabled on AC in the Balanced plan, and this desktop has no battery), still uses "run as soon as possible after a missed start", and no longer requires "a network connection" (that gate skips silently; a run without network fails loudly). Tasks remain "run only when the user is logged on" (InteractiveToken: no stored password, and the failure message boxes need a desktop). **Why:** on 2026-10-14 Windows Update restarted the PC at 04:07 and 04:09, nobody signed in until 08:49, and both daily jobs were missed with no catch-up -- a logged-on-only task can't run at the sign-in screen, and the missed-start catch-up didn't fire at sign-in. On 2026-10-05 a *hibernate* (session kept) was caught up at 09:36 on resume; Modern Standby nights ran on time. The tasks call `run <job> --scheduled`, which exits 0 and writes nothing when the job's latest due run already has a line in `scheduled_runs.log` (any outcome), so sign-ins never repeat a run or a failure box, and a log job's MISSED box shows once per missed slot. **Still exposed:** an update restart that leaves the PC at the sign-in screen until after a slot closes (Thursday: the first kickoff, evening; Sunday: 10:00 Pacific). Windows' "Use my sign-in info to automatically finish setting up after an update" or active hours that keep restarts out of 06:00-07:00 close that gap; both are the user's Windows settings, not changed here. Woken late the same day, `log` decides from the real kickoff instants (logs if the window is still open, refuses if not). Woken on a *different* day, a log job refuses to run at all (`MISSED`): by then `--auto` would resolve to the next week and log it days early.
- The refresh step exists because `log` refuses on a weekly-roster file older than 3 days — without it a Sunday run could never pass. It only rewrites files in `nflverse_raw/`; the loader, `fetch-snaps`, `score` and `report` remain the manual weekly cycle, and `log` refuses if the DB is behind.
- **A scheduled `log` is a real, permanent ledger entry.** `tr_runs.repo_git_commit` records `HEAD` at run time, so commit tracker changes before a slot is logged.

## What a fresh session would get wrong
- **`log` runs `score_week.py` itself and writes the committed prediction files.** Don't hand-run it for the same snapshot. First run of a week keeps the bare name (`2026_week05.json`, what `verify_week.py` reads); a later one becomes `_sunday`. It never overwrites.
- **The ledger is append-only and `log` refuses re-logging a (season, week, slot).** Never test against the real DB — use `--db <copy> --predictions-dir <scratch> --export-dir <scratch>` (and `--as-of` only for testing). A bad real run is permanent.
- **`nfl_games.kickoff_utc` is US/Eastern, not UTC.** Reuse `score_week.parse_kickoff_utc`; don't re-derive it.
- **Scoring reads the raw `stats_player_week_<season>.csv`, not the DB** — the DB loader never carried the 2-pt columns. Spike baselines walk back through consecutive on-disk seasons and stop at the 2019 gap.
- **The tracker doesn't replace `verify_week.py` / `verification_log.json`** — both still run and still use the 4-pt `spike_flag`; numbers can differ slightly.
- **`u50` is strictly `<50` for players whose ownership is known, and a pool player with NO row in the snapshot used stays IN it, flagged as "ownership unknown"** (user decision, 2026-10-05; `sleeper_pool_rule: under-threshold-or-unknown-v2` plus the ids in `run_config_json`). The flag is `tr_pool.percent_owned IS NULL` with `in_u50 = 1` — unknown is not treated as 0% or as under 50%, the player just isn't silently lost, and reports show the count per run. Week 4's run (no `sleeper_pool_rule` key) dropped such players — one, Mike Washington Jr. — and reports say so. Two things to keep in mind: with **no snapshot at all** there is still no sleeper pool (everyone would be "unknown"); and a widely owned player whose ESPN id fails to map to a gsis id would enter the sleeper pool as unknown — `log` prints the names every run and raises a banner when fewer than 80% of the pool matched.
- **Which roster-% snapshot a run uses:** the newest successful ESPN snapshot no older than 36h at log time (`ownership_max_age_hours`); failing that, one live attempt; failing that, the run is logged without ownership and has no sleeper pool. It never falls back to an older snapshot. A snapshot older than 12h at log time (`ownership_stale_note_hours`, i.e. not that morning's) is used but footnoted in reports. Measured so far, 1-2 of ~320 pool players cross 50% per day outside a waiver run; nothing measured across one yet.
- **A 1-week report is not a result.** Don't cite tracker numbers until the small-sample note goes away.
- Windows: native Python won't resolve Git-Bash `/c/...` paths inside Python code; use `C:\...` or relative paths. Tests: `python -m unittest discover -s tracker -v` from the repo root.
- **A live `log` fetches the injury report; an `--as-of` run does not** (today's report would be from that run's future) and records `injury.source: skipped`. Tests that exercise the rule patch `tracker.utcnow` and `tracker.injuries.fetch_nflverse` instead of passing `--as-of`.
- **A live `log` also asks Yahoo who is available in the league; an `--as-of` run does not** (and adds no section). Tests must never reach Yahoo: `TestLogInjuryPoolRule.log_live` passes `--skip-league-availability` unless the test sets `league_fetch`, and patches `league_availability.fetch` either way. For a scratch dry run of the real thing, also pass `--league-raw-dir <scratch>`. The fetch refreshes `league/yahoo_token.json` when the token has expired (hourly) — that is expected; if a refresh ever fails the section says so and the fix is re-running `league/yahoo_auth_step1.py` / `step2.py` signed in to the Yahoo account that is actually in the league (the user has a second Yahoo identity with no leagues, which yields an empty or 403 answer; `users;use_login=1/profile` shows which one a token belongs to).
- **`take_snapshot` needs an explicit raw dir** (no default, on purpose) — a test that forgets it fails instead of writing into the real `raw/ownership/`.
- First loggable slot at handoff: week 4 `sun`, any time before 1:00 PM ET Sunday 2026-10-04 (the pool excludes PIT/CLE, already played, and IND/WAS, the 9:30am London game); the `tracker-log-sun` task will log it at 07:00 local that morning if it hasn't been logged by hand. Otherwise week 5 `thu`.
