# FAAB-Bot

A personal Fantasy Football analysis assistant, built for one person's 12-team Yahoo league. This file is standing context for Claude Code sessions in this repo — written for a reader who knows nothing about the project yet.

## Project

**O.D.D.S. ("Omega Deep Dart Sleeper")** is an XGBoost model that ranks low-usage NFL players by their likelihood of a breakout ("spike") week. It's built for waiver-wire and deep-roster decisions — finding the player whose opportunity is about to expand — not for start/sit calls on players already known to be good.

Honest performance, from a strict out-of-time test (trained 2010–2024, evaluated once on 2025): **precision@10 ≈ 28%**, against a base spike rate of **≈4.3%** — roughly a 6–7x lift over random. That's a useful weekly signal, not a predictor of individual outcomes. It's a **ranking** tool: it will be wrong most of the time, by design.

That number describes the **10-feature** model actually used for that held-out test. The current production model has since been promoted to **13 features** (Group 1 — see Methodology rules) and trained on 2010–2025; it has not yet had a genuine held-out test of its own (see Backlog), so treat its real-world precision as unconfirmed until a future season settles it.

Yahoo Fantasy API access (read-only) works as of 2026-10-10. It feeds the tracker's "Available in my league" section in the prediction markdown (display only) and a local-only league data layer -- daily snapshots of transactions, FAAB, rosters and scores, plus a "league activity" report -- and, from 2026-10-13, the weekly league recap (newsletter v1, built from that data layer and the tracker's scoring). All three are described below. Roster-% for the tracker still comes from ESPN, not Yahoo (see Data sources).

## League settings

- 12 teams, head-to-head
- **Half-PPR**: 0.5 points per reception
- **Single-QB** (not superflex)
- Scoring (read from the league's Yahoo settings 2026-10-13; `league/league_data.py check-scoring` re-checks it): 6 pt rushing/receiving TDs, 5 pt passing TDs, 0.04 per passing yard, 0.1 per rushing/receiving yard, -2 per interception, -0.5 per sack taken, -2 per fumble lost, 2 per 2-pt conversion, 0.02 per return yard, 6 pt return TDs and offensive fumble-return TDs, -4 per pick-six thrown. The tracker scores all of it except the pick-six (no column for it in nflverse's weekly stats); the O.D.D.S. training labels still use the older, simpler profile (see Backlog)
- Roster: QB / WR / WR / RB / RB / TE / FLEX + 4 bench + IR
- 6-team playoffs, weeks 15–17
- Waivers run on **FAAB** (Free Agent Acquisition Budget bidding), not priority order

The small bench (4 spots) is why waiver-wire churn matters more than draft night in this format — there's little room to stash upside, so identifying the right add *this week* is high-leverage. That's the whole reason O.D.D.S. exists.

**Pipeline run order** (from repo root):
```
data/init_history_db_schema.py             # create schema
data/refresh_manifest.py                   # resolve nflverse asset URLs
data/fetch_nflverse_history_v5.py          # download season stats
data/load_nflverse_into_history_SAFE_v3.py # load into SQLite
data/load_players_into_ref.py              # player names/positions
model/generate_labels_and_breakouts.py     # spike labels
model/generate_player_week_features.py     # feature table
model/train_production_model.py            # train
model/score_week.py --season Y --week W --json-out predictions/<Y>_week<NN>.json
evaluation/verify_week.py --season Y --week W   # after the week completes and labels exist
```

**Weekly in-season cycle**: run `data/fetch_weekly_update.py --season Y` first, every week, before `generate_labels_and_breakouts.py`/`generate_player_week_features.py`/`score_week.py` -- it refreshes stats, games.csv, AND both roster files (`roster_<season>.csv`, `roster_weekly_<season>.csv`) in one idempotent call. **Roster files specifically must be refreshed every week, not just stats/games**: `score_week.py`'s team-changed and new-competitor checks (and the availability gate) read `roster_weekly_<season>.csv` directly, and any cut, signing, or trade since the last fetch is invisible to them until it's refreshed -- a stale roster file silently produces wrong suppressions with no error, which is exactly what happened for two full weeks before anyone noticed. `score_week.py` now warns loudly (not silently) if that file looks stale, but the warning is a backstop, not a substitute for refreshing it.

**Weekly schedule (in season; W = the week about to be played):**
- **Tuesday, after Monday night's stats are published** -- the only time the DB is loaded: `data/fetch_weekly_update.py --season Y`, then `tracker.py check-stats --season Y` (has nflverse corrected the stats of a week that is already scored? If so, `tracker.py score --week N --force` appends a corrected scoring -- nothing is overwritten, and reports read the newest), then `data/load_nflverse_into_history_SAFE_v3.py --seasons Y --through-week <W-1>`, then `model/generate_labels_and_breakouts.py --seasons <all loaded seasons incl. Y> --through-week <W-1>`; then `tracker.py fetch-snaps`, `verify_week.py` and `tracker.py score` / `report` for week W-1, and last `league/newsletter.py build --week <W-1>` (it reads that morning's 06:35 league snapshot, which already holds the finished week's lineups, and the tracker scoring just made; run `league/league_data.py snapshot` first if the scheduled one failed). **Always pass `--through-week <W-1>`** (it caps the latest season at the last completed week): an uncapped load run after week W's Thursday game pulls that game into the DB, which changes `starter_absent_proxy` for everyone who hasn't played yet (see Known model limitations).
- **Thursday and Sunday mornings** -- the `log` tasks run on schedule (see Scheduled tasks below). They refresh the nflverse files but never load the DB.
- `tracker.py log` enforces both sides and refuses (nothing written) if an already-played game from a week before W is missing from `player_week_stats`/`labels_player_week`, or if either table holds **any** row for week W itself.

**Tracker cycle** (on top of the above): `tracker.py snapshot-ownership` daily (ESPN roster-%, append-only; the ESPN endpoint is unofficial, so failures are logged loudly and never fatal), `tracker.py fetch-snaps` after each week's nflverse update, `tracker.py log --slot thu|sun` BEFORE the slot's cutoff (it refuses afterward; it runs `score_week.py` itself, so don't also hand-run it for the same snapshot), `tracker.py score` after Monday night, then `tracker.py report`. The ledger is append-only: a bad run can't be edited out, which is why `log` also refuses on a stale roster file, when any already-played game from an earlier week of the season is missing from `player_week_stats` or `labels_player_week` (the model would be scoring on incomplete history), and when either table already holds rows for the week being logged (an uncapped mid-week load -- see Weekly schedule above).

**Season summary (`tracker.py report --season Y`):** the official season record uses one run per week, the first snapshot (`thu` when the week has one, else `sun`) -- cite only that. The same file always carries a second section, "Observation only: Sunday runs", with the same numbers from each week's `sun` run, and a "Thu vs Sun" line per model (difference in top-10 spike hits over the weeks with both slots: the value of Friday/Saturday information). Both are printed every week regardless of which looks better. No confidence interval or "ahead of chance" verdict is printed for fewer than 3 weeks. **Breakout trends (observation only, from 2026-10-22, `tracker/trends.py`):** a further section, "Observation only: breakout trends", shows multi-week payoff, snap- and target-share growth, crowd hits and league adds for each week's official run against the same dart draws, as pre-registered in `docs/tracker_handoff.md` (decision 15). Its definitions are hashed apart from the official record (`hit_config.json` `trend`), and it prints no interval before 8 resolved weeks. `score` appends the outcomes (`tr_trend_outcomes`) as windows close.

**Slot rule:** the `sun` slot closes at the first **1:00 PM ET** Sunday kickoff; `thu` closes at the first game before that. International/early-Sunday games (the 9:30am ET London kickoffs) are treated like Thursday games: they don't close the `sun` slot, and — like Thursday players — their players are left out of the `sun` pool, whenever the run happens. A week with no game before the 1 PM slate has no `thu` slot.

**Pool rule v3 (from 2026 week 6 `sun`; `exclude-no-game-off-roster-out-doubtful-v3`):** on top of v2 below, a player who is **not on an NFL roster** per nflverse's weekly roster -- newest row at or before the week is `CUT` or `RET`, no row this season at all, or no row for the week although his team has rows (a team on a bye has none, so a missing row only counts then) -- is left out for every model, baseline and dart draw (`tracker.split_pool_off_roster`, sharing `score_week.off_roster_reason`). `score_week.py` leaves them unscored itself (`off_roster_watch_list`) and puts `EXE` (exempt list) in its availability gate. Found 2026-10-15: Andy Dalton, released by PHI in week 5, ranked in the week 6 `thu` pool on his stats-history team; that run had 20 such players (left as logged, footnoted from the committed `tracker/off_roster_audit_20261015.json`, as are the three earlier runs). A roster file that would put more than 25% of the candidates off a roster is treated as broken: `score_week.py` skips the check with `[ROSTER WARNING]` and `log` refuses. Each run keeps a gzip copy of the roster file it used (`raw/rosters/`) and its SHA-256; Yahoo's player status (`NA` = "Inactive: Coach's Decision or Not on Roster") is stored as a cross-check only. **(FA)** flags a player the tracker's rule caught that `score_week.py` didn't. **Practice-squad (`DEV`) players stay in -- an open question.** `verify_week.py`: week 7 is the first snapshot with the check (`pool_changes` marker). **Pool rule (from week 5):** a player whose **team has no game that week** (a bye), or who is designated **Out or Doubtful** on the week's NFL injury report at log time, is left out of the tracker's pool, for every model and baseline alike (`tracker.split_pool_no_game`, `tracker/injuries.py`; rule version `exclude-no-game-out-doubtful-v2` and the excluded ids are stored with each run). The bye part was added 2026-10-08 after the week 5 `thu` run was logged with 26 bye-week players in its pool (footnoted in reports, left as logged); Since the same day `score_week.py` leaves bye-week players unscored itself (`no_game_watch_list`; the tracker's rule remains as its own guarantee and would flag any it still caught **(BYE)** in the prediction markdown). For `verify_week.py` that makes week 6 the first week without ranked bye-week players; week 5's first snapshot is frozen with them (see the `pool_changes` marker in `predictions/verification_log.json`). The rule's source is nflverse's `injuries` release, fetched by `log` itself; ESPN's `injuryStatus` from the pinned roster-% snapshot is a stored cross-check and the fallback when the nflverse file is missing or stale. **From 2026-10-18 `score_week.py` applies it too:** an Out/Doubtful player is not ranked; he is listed in `injury_watch_list` (the JSON) and under "Out/Doubtful (not ranked)" (the markdown), Questionable players stay in. One definition in `tracker/injuries.py` (`rule()` reads the statuses and age limits from `hit_config.json`, `excluded_ids()` decides): `log` resolves the designations once -- before running O.D.D.S. -- and hands them to `score_week.py` with `--injury-designations`, so both apply the very same report; a run by hand resolves them itself (`injuries.resolve_standalone`: same nflverse source, ESPN fallback from the newest roster-% snapshot within 36h, never a live one); an `--as-of` run or `--skip-injuries` applies none. The check is applied last, to the players who would otherwise be ranked, so `injury_watch_list` is exactly the set the pool rule used to exclude (checked by replaying the week 6 `sun` run: identical pool, picks and exclusions). The tracker's own split stays as the guarantee, and the **(OUT)** / **(DOUBTFUL)** flags (and their legend) now appear only for a ranked player it still catches. `verify_week.py`: week 7 is the first snapshot with the check (`pool_changes` marker).

**League availability view (display only, from 2026-10-10):** at `log` time the tracker asks Yahoo which QB/RB/WR/TE are free agents or on waivers in the user's own league (`tracker/league_availability.py`, through `league/yahoo_auth.py`), maps them to gsis ids (the weekly roster's `yahoo_id` column, then a unique name + position match on the weekly roster, then on `ref_players`; never a guess), and appends an **"Available in my league"** section to each prediction markdown: that model's 25 highest-ranked pool players who can actually be picked up (`league_available_top_n` in `hit_config.json`), with its own rank and score and free-agent vs waiver status. It is display only -- it runs after the pool is final and nothing reads it back, so the pool, scores, ranks, picks, the prediction JSON and `verify_week.py` are unchanged (tested: the same run with and without it writes identical `tr_pool` / `tr_predictions` rows). The snapshot is stored with the run, append-only: `tr_league_snapshots` (status, counts, the raw response's SHA-256 and file name) and `tr_league_availability` (one row per available player, with how it was matched), the raw response as a gzip file in `raw/league/`. If the fetch fails (or hangs: it is cut off after about 3 minutes) the run logs as usual, the failure is stored as an `ok=0` snapshot and the section says availability was unavailable. An `--as-of` run or `--skip-league-availability` fetches nothing and adds no section. **The league key lives in the gitignored `league/.env` as `YAHOO_LEAGUE_KEY` (`<game>.l.<league id>`, a lower-case L; the game key changes every season) and must stay out of committed files -- this repo is public.** The committed ledger export carries the snapshot's hash and counts, not the key; the section itself (NFL player names and FA/waiver status) is committed with the prediction markdown.

**League data layer (from 2026-10-10; `league/league_data.py`, local only):** a daily job snapshots the user's own Yahoo league into append-only `lg_*` tables in the history DB -- every team's remaining FAAB and waiver priority (`lg_teams`), the whole season's transactions with the winning FAAB bid on each waiver add (`lg_transactions`, `lg_transaction_players`), current rosters with lineup slots and, from 2026-10-22, Yahoo's player status (`lg_rosters`; `''` = no status, NULL = an older snapshot), every week's matchups and scores (`lg_matchups`), the league's roster slots and scoring rules (`lg_roster_slots`, `lg_scoring_rules`), and each team's FINAL lineup of a completed week with every player's fantasy points (`lg_lineups`; one call per team per week because the league-wide roster call returns no points -- each run refetches the latest completed week and backfills any completed week not stored, and `week_lineups()` reads a week from the newest snapshot holding it) -- one `lg_snapshots` row per resource per run with the raw response's SHA-256, the raw responses as gzip files in `raw/league/`. Each run stores the full current picture; a resource that fails is recorded as an `ok=0` snapshot and the others still land. `league_data.py report` writes `league_data/league_activity_week<NN>.md`: per manager, the transactions of the current league week and the two before it (Yahoo's own week boundaries), FAAB left and spent, an **active bidder** flag (2+ bids in the window, $0 bids included -- a $0 bid is interest), **paid bids** and a **typical paid bid** (count and median of the bids above $0, winning and losing), a **funded active bidder** flag (active, at least one paid bid in the window and at least `FUNDED_MIN_FAAB` = $10 FAAB left; `report --funded-min` overrides), "decided by waiver priority" on any award won at $0 over a $0 next offer (Yahoo's winning amount where the award is linked), and the margin of each of the user's winning bids over the next offer. **Yahoo's API has no losing bids** (checked against ~35 routes: only successful transactions are listed, and other teams' pending claims are refused), and Yahoo's terms don't allow tools that extract data from its pages, so **nothing parses or automates the website**: the user types losing offers into `league_data/manual/bids.csv` (`award_date, player, winning_team, winning_amount, losing_team, losing_amount`; one row per losing offer) and runs `league_data.py import-bids`. **Team names in the file are matched by team id, not text:** every name a team has ever had in the snapshots and every manager nickname resolve to that team (`league_data.team_index`), so a team renamed mid-season answers to its old and new name, before and after the rename; case, spacing and apostrophe style don't matter (`name_key`: Yahoo writes `I’m`, a keyboard `I'm`); a name or nickname two teams share is rejected, never guessed. The file is the whole truth at each import: new rows are added, a changed row is appended as a correction (newest version wins, the old one stays on record), a removed row is appended as withdrawn -- `lg_bids` is append-only like everything else. Every award is linked to the API's waiver add (same player, within a day), and one whose typed winning team or amount differs from Yahoo's is flagged at import and in the report. With losing offers entered, the flag counts all bids; without any for the window it falls back to winning claims and says so. **`# checked_through: YYYY-MM-DD`** (from 2026-10-14): a line in `bids.csv` that the user moves forward only after going through the FAB Offers page. It is stored with each import (`lg_bid_imports.checked_through`), and the report then calls an award on or before that date with no losing rows "uncontested" and a later one "not typed in yet" (and, when the date reaches into the window, counts all bids even if the window has no losing offers). Missing or blank, the report keeps "uncontested, or not typed in yet"; a date that can't be read, a second such line or a date after the import day is reported as rejected and stored as not set. Only the first CSV cell of the line is read, so a spreadsheet save (trailing commas, quotes) doesn't break it. The newsletter's team section still uses the unsure wording. **Everything this layer produces names the league or its managers and stays out of the repo**: the DB, `raw/`, `league_data/` (report and `manual/bids.csv`) are gitignored, error messages are scrubbed of the league key, manager guids and images are never parsed, and the tests and the committed fixture (`league/fixtures/bids_synthetic.csv`) use a made-up league. Tests: `python -m unittest discover -s league -v`.

**League newsletter (v1, from 2026-10-13; `league/newsletter.py`, local only):** after the Tuesday cycle, `python league/newsletter.py build --week <W-1>` writes a weekly recap of the user's league to `league_data/newsletter/<season>_week<NN>/`. **Facts first:** code computes every number and name into `facts.json` (with a readable `facts.md`); the renderings are templates that print fact fields, and `check_text` / `newsletter.py check` verifies any prose -- template output or something written by hand -- by looking up every number and every known name in the facts its audience may see. Prose may never add a fact. **Renames:** names are always the current ones; a team whose name differs from the one it had when the recapped week began gets a one-time `team_renamed` fact and a "(formerly ...)" note in the standings and the group chat (the next week's starting point already has the new name). **Audiences:** every fact carries `audience` = `league` (what all managers can already see on Yahoo -- scores, standings, lineups, transactions, FAB Offers bids -- and arithmetic on it), `team:<id>` (analysis for that one manager: which bench player should have started, the margin over the next bid) or `owner` (the installation owner's private analysis: other managers' bidding profiles, what O.D.D.S. ranked highest among players available in the league). A rendering is handed only the facts visible to its audience (`league` < `team:<id>` < `owner`, the owner seeing league facts, the owner's own team's and owner facts), so a template cannot print what it was never given; a test rewrites every owner and team fact with marker values and asserts none reaches a league or other-team rendering. v1 writes `league_recap.md`, `league_groupchat.txt` (short) and `owner_recap.md`. **No hardcoded "me":** every per-team computation (bench report, bid margins) takes a team id and is computed for every team; "my team" is only the default of `--team` (`league_data.default_team`: the team Yahoo says the logged-in account owns). **What it computes:** results, high/low and top scorers, standings and streaks, all-play record and luck (actual wins minus the wins the all-play rate would have earned), points left on the bench (best possible lineup minus actual), the week's transactions, winning and hand-entered losing bids and FAAB, and an O.D.D.S. line framed as fun, not advice. **Scores:** the official result is Yahoo's scoreboard score; in 3 of 60 team-weeks (2026-10-13) the starters' points didn't add up to it -- each time by exactly one starter's negative total, though another negative-scoring starter was counted normally -- so the difference is recorded as a `score_check` fact rather than explained. Output names teams and managers and is gitignored; tests use a made-up league. **Direction:** any manager could eventually be given his own team-specific output (that is what `team:<id>` is for), but owner-only intelligence -- bidding profiles, anything from O.D.D.S. or a crowd model -- stays private for now.

**Sleeper (under-50%) pool:** built from the newest successful ESPN snapshot no older than 36h at log time (older than 12h gets a report footnote; with no usable snapshot the run has no sleeper pool). A pool player with no row in that snapshot is kept in the sleeper pool flagged "ownership unknown" (`percent_owned` NULL), never treated as 0%, and counted in the reports. The ESPN parser skips the odd record that has no `ownership` block (a newly added player) and fails a snapshot only if under 98% of records are valid.

**Scheduled tasks** (Windows Task Scheduler folder `\FAAB\`, registered by `python tracker/scheduled_run.py install`): `snapshot-ownership` daily 06:30, `league-snapshot` daily 06:35 (`league/league_data.py snapshot`, then `report`; its failure is a message box of its own and affects no other job), `log --auto --slot thu` Thursdays 07:00, `log --auto --slot sun` Sundays 07:00 (PC-local time; the log jobs run `data/fetch_weekly_update.py` first, and the Thursday job finishes with an advisory `check-stats` that raises a message box if an already-scored week's stats were corrected -- it never affects the log run or its exit status). Output goes to `tracker/logs/` (gitignored). A week without the slot, or a slot already logged by hand, is a quiet skip; a closed window, stale data, or a run on the wrong day fails loudly (message box + log) without writing to the ledger. From 2026-10-14 each task also fires 2 minutes after sign-in and wakes the PC from hibernate, and runs `--scheduled`: a job whose latest due run is already in `scheduled_runs.log` does nothing (why: a Windows Update restart left the PC at the sign-in screen through both daily jobs; see the handoff). A scheduled `log` is a real, permanent ledger entry — commit tracker changes before a slot is due. Details and known gaps (e.g. week 12's Wednesday game) are in `docs/tracker_handoff.md`.

**Mid-week re-runs and the kickoff guard**: `score_week.py` can be safely re-run for the same week after some games have already kicked off (e.g. a Sunday-afternoon refresh) — it checks each candidate's actual game kickoff instant (from `nfl_games.kickoff_utc`, resolved as US/Eastern local time and converted to real UTC via `zoneinfo`; that column is NOT true UTC despite the name, confirmed directly against 2026 data — see `score_week.py`'s module docstring for the full check) against `--as-of` (default now), and excludes anyone whose game has already started rather than re-scoring them. Their rank/score is carried forward from the week's first committed snapshot instead, never recomputed. A later same-week run must use a different `--json-out` (a snapshot label before the extension, e.g. `2026_week04_sunday.json`) so it doesn't overwrite the first — `evaluation/verify_week.py` is unchanged and only ever reads the bare, unsuffixed filename, so the first snapshot stays the sole authoritative record for the running log and the shadow head-to-head.

The SQLite database, `nflverse_raw/`, `raw/`, `tracker/logs/`, and all `.joblib` model files are gitignored (regeneratable/binary) — every script resolves their paths relative to the repo root via `Path(__file__).resolve().parent[.parent]`, not a bare relative string, so they work regardless of which directory a script is invoked from.

## Known model limitations

- **QB scores are unreliable.** The dominant feature, touch share (carries + receptions), measures only rushing volume for a QB — a proxy for mobility, not for role or passing workload. A simple passing-volume feature (Group 2: trailing pass attempts, trailing pass air yards) was tried and **rejected** — see Methodology rules — so this limitation stands; a richer, play-by-play-derived version remains on the backlog.
- **No concept of teammates competing.** Touch share is computed per player, so two backs splitting one backfield can both rank highly without the model registering that they're taking carries from each other. A candidate fix (Group 3: `trailing_position_group_rank`, `trailing_share_of_position_group`) was tried and **rejected** — see Methodology rules — so this limitation stands.
- **`starter_absent_proxy` leaks the week being predicted (found 2026-10-03, not yet fixed).** It's one of the 13 production features. In the training table (`features_lib.py`, `compute_schedule_dependent_features`) it is 1 when the presumed starter did NOT play in the very week being predicted — knowable only after the games — and is populated for ~94% of rows; in live scoring that week has no data yet, so it's `None` for every row. That breaks the "strictly before the week" rule and creates train/serve skew (importance is small, ~1% gain). **It also makes live predictions depend on DB load timing** (found 2026-10-03): the feature is `None` only while the DB holds no stat rows for the week being scored. Once any are loaded -- e.g. the loader run after that week's Thursday game -- `score_week.py` computes it from the partial week and it becomes 1 for every non-starter whose team simply hasn't played yet, so the same Sunday run scores differently depending on when the DB was last loaded. Contained for now by process, not fixed: `--through-week` on the loader and labels generator, and `tracker.py log` refusing on a DB that holds current-week rows. That refusal covers the whole exposure: `player_week_stats` (and the labels built from it) is the only place the feature code reads current-week data from. No feature of either model reads game results -- `home_score`/`away_score` appear nowhere in `features_lib.py` or `score_week.py`; from `nfl_games` only the schedule is used (teams, Thursday flag, playoff flag, kickoff time), and `team_week_stats` only supplies the pre-game lines of the rejected Group 4 features, which neither model uses. Checked 2026-10-03 by scoring week 4 on two DB copies that differed only in week-4 scores and lines: every production and shadow score was identical. The label-shuffle check planned for the tracker's backtest would NOT catch this kind of leak (shuffled labels stop matching the leaking feature too); the right detector is an as-of recomputation diff (compute week W's features with week W-onward data removed and diff). Fix is queued (see Backlog).
- **A player who is not on an NFL roster is not scored** (from 2026-10-15; released/retired/unsigned per the weekly roster, listed in `off_roster_watch_list`), and the exempt list (`EXE`) joined the availability gate. Before that, eligibility only asked for a game this season or last, so unsigned veterans and released players were ranked on their stats-history team. Week 6's first snapshot is frozen with them (none in either model's top 25).
- **A player whose team has no game that week (a bye) is not scored** (from 2026-10-08; listed in `no_game_watch_list`). Before that the live ranking included bye-week players -- something the training table, which only holds player-weeks that were played, never contained. Week 5 was the only affected week (see `predictions/verification_log.json`, `pool_changes`).
- **Production's scores are not probabilities (found 2026-10-13, weeks 4-5, read-only).** Its top 25 averaged 0.67 predicted against 0.30 realized -- about 2x high -- and 0.41 against roughly 0.12 over the whole pool; the shadow model was roughly calibrated (0.29 against 0.32 at the top). The ORDERING is intact (higher score bands do spike more), so precision@k and the tracker's hit counts are unaffected; never present a production score as a chance of anything. Cause not investigated (both models share `scale_pos_weight` and `starter_absent_proxy`; they differ in the three receiving features). Queued with the retrain (see Backlog).
- **Offseason staleness is handled by suppression, not guessing.** Before a player has games on a new roster, usage features describe a role that no longer exists. `score_week.py` detects this (confirmed team change, or a meaningful new same-position competitor added this offseason — judged by prior-season production or early-round draft capital) and excludes the player from ranking with `score: null` and a reason, rather than publishing a number built on stale data.

## Git discipline (standing rules)

- Run `git status --ignored` before staging, every time.
- Stage exactly the intended files. **Never `git add -A`** — it silently sweeps in generated artifacts (`manifest_nflverse.json`, ad hoc report files, etc.) that don't belong in a commit.
- One logical change per commit.
- After pushing, verify against the remote with `git ls-remote` (or `git ls-remote --tags` for tags) — don't just trust the push command's own output.
- **A local pre-commit hook runs `tools/privacy_scan.py`** (install once per clone: `python tools/privacy_scan.py --install-hook`). It refuses a commit whose added lines contain any team name or manager nickname the league snapshots have ever held (a renamed team's old and new names), any team name typed in `bids.csv`, the league key or bare league id, or this machine's user and computer name -- read at run time from the local, gitignored data, so no list of names is ever committed. Case, spacing and apostrophe style are ignored; a nickname that is part of an NFL player's full name on the line is not a hit. It prints only file, line, the kind of term and its length, never the term. Don't bypass it (`--no-verify`); fix the line.
- Never commit `.env`, `yahoo_token.json`, the `.db` file, `nflverse_raw/`, `raw/`, `league_data/` (league reports and the hand-typed bids -- they name managers; the repo is public), or `.joblib` model artifacts. (Model *metadata* sidecars — `*.meta.json` — are committed; the binaries they describe are not.)
- Use `git mv` for any file move/rename, so history is preserved.

## Methodology rules (standing)

- Train/test splits are always **chronological**, never random.
- Every feature must be computable strictly **before** the week being predicted — no leakage.
- Hyperparameters are tuned on a validation slice carved from the **training** period, never on the test set.
- A test set is used **once**, then considered closed. Don't re-run comparisons against an already-closed test year.
- A new feature is adopted only if it **wins on held-out data against a pre-registered metric** — never because the theory behind it sounds right.
- **Training scripts must specify their training seasons explicitly** — never train on "whatever is in `player_week_features`." That table now grows with live in-season data (`generate_player_week_features.py` rebuilds it across every loaded season, current one included, once it's been run for a week), so an unfiltered train silently leaks current-season weeks into a model meant to score that same season live. `train_production_model.py`'s `TRAIN_SEASONS` constant is the pattern to follow — this is exactly the bug caught (and fixed) during the Group 1 promotion.
- **Evaluation slices (standing designation):**
  - **2024** is the designated development slice for feature-group hypothesis testing (train 2010–2023, evaluate on 2024). It has already been reused across Group 1 and Group 2, so it is **not virgin** — a win on 2024 is a green light to keep developing a group, never by itself a green light to promote it. **Promotion to production requires prospective confirmation on live 2026 weeks** (real weeks scored and verified as they happen), in addition to a 2024 win, because 2024 can no longer distinguish a genuine effect from a group that happens to fit this one reused year.
  - **2023** was reserved as a **second-opinion slice for one future decision** — not for routine group testing. Correction: it was never fully virgin — it was already the validation slice for the `share_delta_vs_prior_season` test earlier in this project (won there, then lost on the 2025 held-out test, the result that actually decided it), so "lightly used," not untouched, is the accurate description. It has now been **spent** on Group 8's pre-registered reserve-slice confirmatory test (see below) — there is no second-opinion slice left in reserve; a future genuinely-close call has no equivalent slice to fall back on.
  - **2025 is closed** — it already decided the 10-feature model's held-out test (see the top of this file). Don't re-run comparisons against it.
  - **2026 weeks cannot be re-scored** for hypothesis testing — `score_week.py` reads live state (current rosters, current injury/suppression signals), not a frozen historical snapshot, so a 2026 week can only be scored once, going forward, as it actually happens. Prospective confirmation therefore means watching new 2026 results accumulate via `verify_week.py`, not re-running `score_week.py` against an already-played 2026 week.

Eight feature candidates have been **rejected** by this discipline: a usage-trend feature (negligible importance); a season-over-season touch-share delta (won on a 2023 validation slice, then lost on the 2025 held-out test — the result that actually decided it); Group 2, QB volume (trailing pass attempts, trailing pass air yards, team WR-target rate) — it won pooled precision@10 on a 2024 re-test, but a per-position re-evaluation showed that win traced entirely to the model reallocating picks toward QBs (a ~4x higher base rate than the pooled population), with essentially no movement at RB, WR, or TE; Group 3, teammate competition (`trailing_position_group_rank`, `trailing_share_of_position_group` — rank/share of trailing touches among a player's own team's players at the same position, competition-style ranking on ties, single-player groups rank 1 with share 1.0; NULL for QB) — the same pattern as Group 2: it won pooled precision@10 on the 2024 development slice (0.2889 → 0.3167, +0.0278), but *lost* at every one of RB/WR/TE, the primary per-position metrics (RB −0.0167, WR −0.0167, TE −0.0056); Group 4, Vegas lines (`implied_team_total`, `game_total`, `team_spread`, looked up from `team_week_stats` for the player's own upcoming game — not a trailing window, so not leakage) — the opposite pattern: it *lost* pooled precision@10 on 2024 (0.2944 → 0.2722, −0.0222), with a mixed, mostly-noise-level per-position result (RB −0.0111, WR +0.0000, TE −0.0056, QB +0.0167), and even setting that weak signal aside, its 2026 NULL rate is a decisive **82.4% overall** (0% for the three already-played weeks, 100% from week 4 on) — Vegas lines aren't posted more than about two weeks out, which would make the group largely unusable for live scoring most of the season regardless of test results; and Group 5, trailing efficiency (`trailing_racr`, `trailing_receiving_epa`, `trailing_rushing_epa` — per-game trailing averages straight from `player_week_stats`, where a NULL raw value already encodes "no qualifying denominator that game"; `trailing_racr`/`trailing_receiving_epa` NULL for QB, `trailing_rushing_epa` NOT position-gated since it's real signal for a rushing QB too) — this one won BOTH pooled (0.3222 → 0.3333, +0.0111) AND RB/WR precision@10 (RB +0.0556, WR +0.0389; TE −0.0111, QB −0.0333), which would normally be the strongest result on record after Group 1. It's rejected anyway on a different, pre-registered concern: `spike_flag` is defined relative to a player's own trailing-3-game **points** baseline (`generate_labels_and_breakouts.py`), so a depressed efficiency stretch mechanically *lowers* that baseline and makes an unrelated point total easier to clear as a "spike" — a labeling artifact, not real signal. `evaluation/test_efficiency_features.py`'s confound check confirmed the artifact's fingerprint directly: spike rows have **systematically lower** trailing efficiency than non-spike rows on all three features (racr −0.107, receiving EPA −0.174, rushing EPA −0.275), the wrong direction for a "efficient players are due for more volume" story and exactly the direction the baseline-depression mechanism predicts. Pooled precision@k alone can't be trusted to catch a reallocation artifact, and — as Group 5 shows — neither can a good per-position result on its own when the label itself has a mechanical dependency on the candidate feature; per-position precision (`evaluation/metrics.py`) plus this kind of label-mechanism check are both now standard for a feature-group test. Group 7, line quality (`trailing_team_sack_rate_allowed`, `trailing_team_stuff_rate_allowed`, `trailing_opp_sack_rate_generated`, `trailing_opp_stuff_rate_generated`, sourced from `team_week_pbp_stats`; not position-gated) is the first group where all four features are TEAM-level rather than player-level — every player sharing a team, or facing the same upcoming opponent, gets the identical value that week (confirmed directly: ~19 rows/value for the team-side features, ~30 for the opponent-side ones, which have zero player-specific dispersion by construction). It won pooled precision@10 on 2024 (0.3056 → 0.3167, +0.0111), but the per-position read is a genuine mixed result, not a clean artifact or a clean win: RB dropped sharply (−0.0556), while WR gained (+0.0389) and TE was flat (+0.0056). Feature importances show the model does use it somewhat — 2.2% combined gain, ranked 9th/12th/13th/15th of 17 features, ahead of several established production features — so this isn't a case of the model ignoring a duplicated-value column; it's a real but net-negative effect concentrated at RB, the position where blocking quality plausibly matters most, which is what makes the drop notable rather than a favorable modeling choice. Group 8, red-zone opportunity (`trailing_rz_carries`, `trailing_rz_targets`, `trailing_rz_share`, `trailing_team_pass_rate`, sourced from `player_week_pbp_stats`/`team_week_pbp_stats`; deliberately NOT position-gated, since RBs get real red-zone targets and rushing QBs get real red-zone carries) is sparse by construction — `trailing_rz_carries` is 0 for 94.4% of WR rows and 97.8% of TE rows, `trailing_rz_targets` is 0 for 53.7% of RB rows and 98.2% of QB rows, all real zeros (no qualifying carry/target that week), not missing data. It won pooled precision@10 on 2024 (0.3000 → 0.3278, +0.0278), with the now-familiar mixed per-position pattern: RB −0.0222, WR +0.0056, TE +0.0222 — the same RB-down/others-up shape as Groups 3 and 7. Combined importance was ~2.8% of total gain, ranked 7th/8th/11th/13th of 17 features — used, not ignored. `evaluation/label_distribution_by_season.py` found separately that 2024 has the **lowest RB spike rate of all 15 full seasons** (rank 1/15) — a real property of that slice's labels, not of any one candidate feature — which is offered as context for why RB has now underperformed on 2024 across several unrelated feature groups, not as an explanation this test itself established.

Group 8 was then given a confirmatory test against the 2023 reserve slice (`evaluation/test_red_zone_opportunity_2023_reserve.py`), spending it per a **pre-registered decision rule fixed before the script ran**: train 2010–2022, evaluate on 2023; pass only if the sum of the RB/WR/TE precision@10 deltas is positive AND none of those three loses more than 0.02 (QB secondary, pooled reported for continuity only, neither decisive). **Result: FAILED.** RB −0.0056, WR −0.0056, TE −0.0167, sum −0.0278 (condition (a), sum > 0, failed; condition (b), no breach past −0.02, was actually met — the rule failed on the sum, not on a single bad position). Group 8 is rejected on this basis, per the rule fixed in advance and not adjusted after seeing the result. Notably, this run's character differs from the 2024 run: on 2024 WR and TE *gained* while RB alone dropped; on 2023 all three RB/WR/TE lost together, a milder RB loss (−0.0056 vs 2024's −0.0222) but no offsetting WR/TE gain to carry a positive sum — so 2024's specific magnitude at RB doesn't fully explain 2023's failure, since 2023's own RB spike rate is unremarkable (unlike 2024's, the lowest of 15 full seasons) and RB still lost. Pooled precision@10 was barely positive on 2023 (+0.0056) despite all three primary positions losing — pooled continuity numbers alone would have masked this rejection, which is exactly why the decision rule is defined on per-position deltas, not pooled.

Separately, a **recency-weighting modification** to 4 existing production features was tested and rejected in both variants: Group 6 applies exponential recency decay to the trailing-window computation behind `trailing_touches_avg`, `trailing_team_touch_share`, `trailing_target_share`, and `trailing_air_yards_share` — same feature *names*, not new columns, via `FeatureEngine.compute_recency_weighted_usage` (decay constant 0.5 per game further back, a 1-game half-life, chosen because usage/role can shift quickly and a flat mean already responds slowly) — against the unweighted production baseline on 2024. Variant A (same 3-game window, weighted) lost pooled precision@10 (0.3056 → 0.2889, −0.0167), RB −0.0333, WR −0.0111, TE +0.0000. Variant B (widened to a 6-game window, same decay) also lost pooled (−0.0278), RB −0.0333, WR +0.0000, TE +0.0111. Neither variant showed a per-position win worth weighing against its pooled loss. `evaluation/test_recency_decay_features.py` is the record of this test.

One candidate has been **adopted**: Group 1, receiving opportunity (`trailing_target_share`, `trailing_air_yards_share`, `trailing_adot`; NULL for QB rows). The same per-position re-test confirmed a genuine, position-appropriate win — WR +0.10 precision@10, TE +0.033 — not a reallocation artifact, and it's now part of `PRODUCTION_FEATURE_COLS` (13 features total). The production model trained on 2010–2025 with this set is `odds_xgb_model_production.joblib`; the superseded 10-feature model is preserved as `odds_xgb_model_production_10feature.joblib` for comparison. `predictions/verification_log.json` carries an explicit `model_changes` marker at this boundary — the production filename didn't change, so `git_commit` (not the filename) is what distinguishes weeks scored before vs. after this promotion.

`evaluation/` holds the record of all eleven tests; don't re-litigate a rejected feature or modification without a genuinely new held-out test.

## Data sources

- **nflverse** ([nflverse-data](https://github.com/nflverse/nflverse-data)) for historical NFL stats. Current fetch source is the `stats_player` release tag — the older `player_stats` tag is deprecated/frozen and lacks 2025+ data. **2019 has a real schema gap** (its `stats_player_week` file predates the modern column layout) and is excluded from training; the season-gap logic throughout the pipeline treats it as a genuinely missing season, not something to bridge across.
- **Roster-%** for the tracker: ESPN's public fantasy endpoint (`percentOwned`, unofficial/undocumented, no auth; platform-wide, not Yahoo's) is primary; Sleeper's trending-adds (counts, not %) is secondary (Sleeper has no ownership field). Yahoo is connected since 2026-10-10 but is used for league data only (next bullet); the tracker's roster-% still comes from ESPN. The DB keeps the parsed rows plus each raw response's SHA-256; the raw responses themselves are gzip files in `raw/ownership/` (gitignored, outside the DB, archivable). **Injury designations** for the tracker's pool rule: nflverse's `injuries` release (official weekly report, 2009 onward, refreshed nightly at 06:00 UTC); a copy of the file each run used is kept in `raw/injuries/`. ESPN's response also carries an `injuryStatus` (editorial, not the official report), stored per snapshot as a cross-check. **Snap counts** come from nflverse's `snap_counts` release (PFR ids crosswalked to gsis via `players.csv`).
- **Yahoo Fantasy Sports API**, read-only, for league data — working since 2026-10-10 (the token needs the `fspt-r` scope and must be authorized by the Yahoo account that is actually in the league). `league/yahoo_test_leagues.py` is the smoke test. Used by the tracker's league-availability view and the league data layer; real league data stays local (`league_data/`, `raw/league/`, the DB). The API does not expose losing FAAB bids -- those are typed by hand into `league_data/manual/bids.csv`; the website is never scraped or automated (Yahoo's terms).

## Reproducibility note

XGBoost training is **not bit-reproducible** across runs, even with a fixed `random_state` (histogram-building order isn't strictly deterministic). A model's metadata sidecar (`*.meta.json`) describes how it was trained — seasons, features, hyperparameters, git commit — not a guarantee that retraining reproduces its exact scores. **Committed files under `predictions/` are the authoritative record of what a given model actually predicted**; never assume a regenerated model will reproduce them.
